# Product readiness review

Evaluate the product as a new user with a concrete job to complete. Inspect the working product, not only screenshots or plans.

## Review

1. State the target user, core job, promised outcome, and first success moment.
2. Walk through discovery, signup or installation, first use, failure recovery, repeated use, and upgrade paths.
3. Check that the website, UI, CLI, API, and documentation use the same concepts and names.
4. Identify dead ends, hidden prerequisites, unclear state, duplicated concepts, and actions without feedback.
5. Verify credibility signals such as working examples, security posture, pricing clarity, support, status, ownership, and realistic claims.
6. Distinguish product gaps from visual polish. Do not recommend a redesign when a missing workflow is the actual problem.
7. Prioritize by user impact, confidence, effort, and dependency order.

Do not change the product or create speculative features unless the user asks for implementation.

## Report

Return:

- `Positioning`: Who it is for, what it does, and why it is credible.
- `Critical journey`: The observed steps and where users fail.
- `Findings`: Evidence, impact, and severity for each problem.
- `Priorities`: Now, next, and later with a measurable outcome.
- `Investor questions`: Claims, risks, traction, or business assumptions that still need evidence.

Keep recommendations specific enough to become issues or implementation tasks.
